# 0.33.1 — 它说"我看不到"的时候，现在知道是为什么

0.33.0 之后重读附件链路，发现四处「说了不知道的事」：上传被拒说成"还没到"、每个文件都读满 96 KB 只为拿三行、"整份"判据反了、第十个附件被静默丢弃。这一版只修这些，没有新功能。

## 四处行为变化

| 变化 | 改之前 | 改之后 |
| --- | --- | --- |
| 上传被拒 | 一律写「宿主还没收到」，模型劝用户"等一下" | 按 `status` 分：`uploading` 等一等、`error` 请重新添加、其余才算没到 |
| 读文件 | 每次先读满 96 KB，再取整份或前三行 | 窗口跟着用途走：小文件读「声明长度 + 1」，大文件只读 8 KB |
| 「是不是整份」 | 用「读到的比声明的少」判断；文件长胖时会被当成完整引用 | 读满窗口就算截断；长胖的文件不会被当成完好 |
| 第 9 个附件起 | 静默丢弃，模型把 8 个当成全部 | 报 `attachmentTotal`，说明里写「还有 N 个没描述」，指纹带 `+N` |

## 三处怎么发现的

**上传被拒**：浏览器把上传状态记在 `fileUploads` 里（`ready`/`uploading`/`error`），插件只看有没有回执。可被拒的上传永远不会变成 `ready`——它是一条死路，不是一段等待。现在描述符带 `status`，缺省 `missing`，所以**旧客户端不升级也不会崩**。

**读文件**：测量脚本用真实 `LocalAttachmentStore` 读真文件——6 KB 文件 0.95 ms/次，588 KB 文件 0.90 ms/次，八个大文件 **6.97 ms/次**，全都为了最后只留三行。

**长胖的文件**：判据原来是「读到的少于声明的 ⇒ 完整」。文件在上传之后被追加内容时读到的会更多，于是它被当成完好的整份引用了。用例：声明 40 B、实际 4400 B，现在 `clipped === true`。

**第十个附件**：`MAX_SENT_ATTACHMENTS = 8` 两端都硬切。更麻烦的是缓存键——删掉第九张图，键一模一样，拿到的是同一个问题的旧答案。现在总数随请求走，指纹写成 `…+10`。

## 顺带：发出几条与看见几条分开记

`stream-end` 除了 `attachments`（发出去几条）现在还有 `attachmentsSeen`/`attachmentsUnseen`（真正解析出几条）。回执失效那条路以前在日志里和「带了一张图且看到了」长得一样，现在分得开。

## 验证

`npm test` 178 → 181（新增两条：第十个附件被点名而不是被丢掉、`attachmentContent` 的计数），浏览器场景 66/66，`check:client` 一致。四处变异各自打红具名用例：`stamp` 去掉 `+N`、客户端 `key` 去掉 `+N`、说明不写「还有 N 个」、宿主忽略上传状态。

## 兼容与升级

- 请求体新增两个可选字段：描述符的 `status`、请求的 `attachmentTotal`。缺省都有兜底，宿主与客户端可以各自先升。
- `docs/PROTOCOL.md` 的字段表已同步；`SECURITY.md` 的边界没变——字节不经过插件路由。
- **`index.js` 变了，升级要重启桌面应用**；只刷新页面（`Ctrl+R`）只换客户端。
