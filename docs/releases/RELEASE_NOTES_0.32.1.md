0.32.1 只动诊断与账本，**补全的行为一行没改**。改的是一件事：量出来的东西，和你真实用出来的东西，得能分开算。

## 起因

某天 24 小时的日志里，2419 条事件有 1697 条是压测脚本打的，真实补全调用 0 条——`stream-end` 全部来自压测。于是「44% 的补全流从没出过首字」这种结论，描述的是脚本，不是人；`ignoredStreak` 到过 1 有 32 次、到过 2 有 6 次，看着像分布，其实是同一批请求来回跑。事后想分开也做不到：日志里没有字段能区分脚本和人。

## 现在怎么分

| | 之前 | 现在 |
|---|---|---|
| 会话 id 以 `probe-` 开头的事件 | 混在 `composer-quill.log` 里 | 写进同目录的 `composer-quill-probe.log` |
| 这类会话的调用 | 计入用量账本 | 不进账本，改为在探针日志里记一条 `probe-usage` |

钱还是照花，只是那笔账不记在「你今天用了几次」里。要加总能加上——`probe-usage` 里有 mode、model 和完整的 usage。

`dev/probes/` 里三个直接跑宿主代码的脚本（`probe-compose-calls`、`probe-context-cap`、`probe-short-draft`）还把 `DSH_COMPOSER_QUILL_STATE_DIR` 钉到临时目录。状态目录在 `index.js` 加载时解析一次，所以这行 env 必须写在 import 之前——写晚一步就无效了。

## 拆出来的第一份真实数据

把历史上被污染的那份日志按「确凿证据」拆开（`cache-miss` 行里的 `epoch`：脚本用 9000+/9200+，真实状态是 0 或两三位数，据此圈出 7 个爆发窗口共 118 次调用）：3112 行 → 真实 2189 行、探针 923 行。

| 真实流量（11-26 起两天） | n | p50 | p90 |
|---|---|---|---|
| 主路径出字 | 27 | 2047 ms | 4393 ms |
| 短草稿（1–3 字） | 28 | 560 ms | 1047 ms |
| 首字（主路径，纯模型时间） | 32 | 1986 ms | 4204 ms |

78 条补全流的终态：出字 44、被下一次输入顶掉 32、空 2。也就是说，「44% 没出首字」是污染数据给的错觉；真实情况是 56% 出字、41% 是你自己下一键顶掉的——那是正常节奏。
