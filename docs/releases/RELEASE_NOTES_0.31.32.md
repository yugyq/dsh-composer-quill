# 0.31.32

三条关于「谁能发起请求」的决定落地，外加一份把这件事写下来的文档。

## 文档：`docs/REQUEST_TRIGGERS.md`

`client.js` 里有五个地方会发起模型调用，各自的守卫散在 effect 里，靠注释和实测记忆维持一致。这份文档把它们列清楚：

- 五个发起方（打字防抖 / 安全网 / 失败重试 / 回合结束 / 手动）各自的前置条件与节流
- `request()` 内部五道闸门的**顺序**（顺序就是优先级）
- 六个一次性闸门各自归属于谁、什么时候清空

它不是理想设计，是代码此刻的行为——改结构时以它为准，行为变了也要先改它。

## ① 手动不消耗重试额度

保持现状并写进文档：手动触发失败后，自动重试仍会给一次。用户在 1.2 秒内会看到状态从「建议失败」回到「补写中…」。

## ② error 优先

同一份草稿先失败、后得到「没什么可补」，屏幕上保留失败原因，不再被抹成空白。

```js
// streamDone
if (unchanged && current.phase === 'error') return
```

边界：真实结果（`ready`）仍然覆盖 error——「这次确实有建议」比先前的失败更可信。两种情况各有一条单测。

## ③ 打字取消重试

保持现状并写进文档：重试 effect 的依赖里含 `draft`，动手即作废那次待发的重试。人的意图优先于机器的排期。

## 手动失败要不要额外提示

**不额外提示。** 由 ①，重试仍会跑一次；由 ②，真失败时错误行稳定显示「建议失败：<原因>」。再叠一个「手动补写失败」的专用提示，会让 1.2 秒内连跳三种文案。

真正缺的是**区分失败来源**（手动/自动），但那对用户没有决策价值——他要的是「再试一次」，不是「哪条路径失败」。
