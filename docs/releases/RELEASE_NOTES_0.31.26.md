# 0.31.26

C 组三条。前两条是设计决定，第三条是笔误。

## 缓存改成真正的 LRU，容量统一 64

缓存键里带草稿，所以每份不同的草稿都是一条。一次连续打字就能填满 128 条的上限，而原来的淘汰是 **FIFO**（命中不刷新顺序）——先掉的正是你最早写下、但反复回到的那份草稿。这恰好是这类插件最典型的使用方式。

现在：

- **命中即移到队尾**，只重排、不触发落盘
- 淘汰最久未用的
- 内存与磁盘同一个上限 **64**（原来 128 / 64，重启后会莫名其妙少一半）

## TTL 从 24 小时收到 2 分钟

原来三处说法互相矛盾：注释写「两分钟」，代码是 24 小时，架构文档写 120 秒。

选择两分钟的理由：它覆盖了「改一改 → 又改回来 → 再改回去」这一轮里的真实节奏；而 24 小时的收益只有「重启后可能命中一次」，偏偏重启会改变 epoch 与事件戳，实际很少命中——代价却是把建议正文（你草稿的续写）在磁盘上留一整天。

## `/history` 的 `at` 恒为 `null`

代码读的是 `event.at`，而 DSH 的会话事件只有 `time`（epoch 毫秒），这个字段从来没存在过。所以 `PROTOCOL.md` 里那个 `"at": "2026-11-18T05:41:37.534Z"` 的示例一直没被兑现。现在按 `time` 输出 ISO 时间。

客户端本来就靠数组顺序排序，所以没有出过可见问题——属于契约层的错误。

## 测试

单测 83 → 87，新增四项：窗口长度就是两分钟、超出窗口即过期（含否定缓存的 10 秒）、命中过的键不被下一个新条目挤掉、历史行带上 ISO 时间。浏览器场景 36/36 不变，连跑两次通过。
