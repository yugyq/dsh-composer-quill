# 方案：采纳可撤销 + 失败可重试

> **状态：已实施（0.31.44）。** 撤销走原生栈优先、`setDraft` 兜底；重试重置自动重试预算。

## 0. 现状（已核实）

| | 现在是什么样 |
|---|---|
| 采纳 | `accept()` 有四个分支：下一句 / 历史尾巴 / 整段改写 / 补写尾巴。前两种和第四种走 `insertText`，改写走 `setDraft`。采纳后**没有任何回退手段**——全仓库没有 undo、没有保存「采纳前的草稿」 |
| 失败 | `dock-error` 是一个只读 `span`，文案 `建议失败：<原因>`。失败后有一次 1200ms 自动重试；那次也失败，屏幕上就只剩一行文字，用户没有任何操作可用 |
| 可用的宿主能力 | `inputActions` 只有三个方法：`insertText(text, capture)`、`setDraft(text)`、`captureInsertion()` |

## 1. 采纳可撤销

### 交互

采纳成功后，状态行在那一行位置显示一个按钮：

```
已采纳 · 撤销
```

点击（或聚焦后按回车）→ 草稿回到采纳前的文本。它在以下任一情况消失：**8 秒过去**、**用户又输入了任何字符**、**换了会话**。

选「一行按钮」而不是快捷键，理由是：`Ctrl+Z` 在 `insertText` 路径上多半本来就能用（原生撤销栈），但在 `setDraft` 路径上不可靠——而用户分不清自己刚走的是哪条路。给一个统一的、看得见的入口更稳。

### 实现要点

1. **采纳前先存**：`accept()` 已经有 `live.draft`（采纳前草稿）；再加一个 ref `undoOffer.current = { before, after, at, sessionId }`，只在 `afterInsert` 里写。
2. **撤销**：优先 `setDraft(before)`；没有 `setDraft` 就不提供撤销（`insertText` 无法反向），按钮不出现。
3. **撤销后要放行**：把 `lastRequested` 清空、`ghost.clear()`，否则安全网会认为「这个草稿已经问过」，撤销后的草稿不会再有建议。
4. **不用 redux**：`undoOffer` 与已迁移的记账同性质，可并入 `useDockBooking`（动作 `accepted` / `undone`），但**这一轮先放独立 ref**，避免同时改记账和新增功能。

### 边界

| 情况 | 行为 |
|---|---|
| 采纳的是「下一句」（输入框原本为空） | 撤销 = 清空输入框，符合直觉 |
| 采纳后又继续打字 | 按钮消失，保留用户已写的字（不做「撤销并丢弃后续输入」） |
| 8 秒内切会话 | 立即作废，避免把 A 会话的草稿写进 B |
| 宿主没有 `setDraft` | 不显示按钮（不做「尽力而为」的假撤销） |

## 2. 失败行可重试

### 交互

`dock-error` 从 `span` 改成 `button`：

```
建议失败：model call failed · 重试
```

点击 → 对当前草稿重新发一次 `compose`。键盘可达（它是按钮，焦点在输入框时按 Tab 也能到——**注意**：有建议时 Tab 被采纳占用，但错误状态下没有建议，Tab 是空闲的）。

### 实现要点

1. 调 `request('compose', draft, true)`：`force = true` 跳过 900ms 去重与「store 已有结果」两道闸门（这两条在「我刚失败、我要重来」的场景下没有意义），但仍受 `enabled` / 409 退避 / 回合进行中 三道约束。
2. **重置重试预算**：点一次就把 `retriedFor.current = null`，让下一次失败时自动重试还能再给一次。否则「手动重试又失败」之后，自动重试的额度已经被第一次失败用掉了，用户再点才有效果——行为会显得忽好忽坏。
3. 点击后立刻把按钮置灰并显示「重试中…」，避免连点打出多次请求（`force` 会绕过 900ms 去重，连点是真的会多发）。

### 边界

| 情况 | 行为 |
|---|---|
| 仅手动模式（`mode === 'manual'`） | 重试按钮照常可用：用户手动点的意图比「自动建议」更强 |
| 回合进行中（`running`） | 按钮置灰（请求会被 `running` 拦下，不如不给点） |
| 失败原因来自超时 | 文案已含原因，重试同样有效 |
| 连点 | 置灰 + `inFlight` 挡住第二次 |

## 3. 两项的共同点与冲突

**共同点**：都只需要改状态行的渲染 + 两个回调，不碰请求机器与判定链（刚拆完，动它性价比最低）。

**潜在冲突**：撤销按钮与「已采纳」的提示共用状态行；重试按钮与「建议失败」共用状态行。三个状态互斥（采纳后 / 失败后 / 有建议），不会同时出现，所以不需要额外的优先级规则——但需要一个明确的状态判定顺序：

```
失败 → 采纳可撤销 → 建议 → 等待中 → 按键提示
```

这个顺序写进 `renderStatusChip`，并由一条场景断言守住（失败与可撤销不会同时亮）。

## 4. 测试

**单测**（纯函数，新增 `undoChipLabel()` / `retryChipLabel()` 或一个 `statusChipKind()` 判定）：

- 五态判定顺序：失败优先于可撤销，可撤销优先于建议
- 8 秒过期后不再返回「可撤销」
- 无 `setDraft` 时不返回「可撤销」

**场景**：

| 编号 | 断言 |
|---|---|
| S38 | Tab 采纳后状态行出现「撤销」；点击后草稿回到采纳前 |
| S39 | 采纳后再打一个字，「撤销」消失且不回退用户的字 |
| S40 | 失败后状态行出现「重试」按钮；点击发出一次 compose |
| S41 | 连点两次重试只发一次请求 |

## 5. 需要你确认的三点

1. **撤销的时长**：8 秒 / 直到下次输入 / 两者取先——我按「两者取先」写
2. **重试是否重置自动重试预算**：我建议重置（理由见上），代价是每次点击最多花两次调用
3. **错误行放不放「重试」两个字**：现在文案已经有原因，再加会被 60 字截断规则影响；我倾向把按钮文案做成 `重试`，原因留在 `title` 里
